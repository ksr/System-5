## Hardware design findings

From `hardware/TIMING-REVIEW.md` unless noted.

- **T1 (High), CPU card:** the 74LS374 (IC1) latches the high address on TPA's *rising* edge, with no guaranteed setup: −102 ns worst case. It works because a typical 1802 is early, but it is a race (intermittent boot failures or wrong reads). Suggested fix: clock the 374 from *inverted* TPA, using a spare 74LS05 inverter (IC6C or IC6E) with a stiff pull-up of about 1 kΩ. That gives about 471 ns of setup at 1.76 MHz. Apply it on the real card, or in a CPU Rev B redesign.
- **T2 (Medium), 6845 card:** register writes end with R/W (= -MWR) rising while E (= TPB) is still high, at any clock speed. It works on the HD6845; confirm with a scope.
- **6845 Rev B as fitted:** IC4 is a 74LS85, not the drawn 74S85, in the address compare gated by -VMA; IC9 is a 74AS175. The timing review used the Rev A netlist; recheck the decode path with the LS85 when the 6845 model moves to Rev B.
- **T3–T5 (Low), 6845 card:** E width against its 450 ns minimum (+18 ns), register-read data setup (−77 ns worst case) and hold (typical only). CRTC reads are rare.
- **T6 (Low), IDE card:** INP 3 into RAM, with drive data held +49 ns past WE. It fails worst case from about 2.2 MHz.
- **C2 (Small), CPU card:** after a boot-EPROM read, its output overlaps the next card by 28 ns plus R13's RC time. See question 5.
- **Not reviewed yet:** the reset/run circuit (IC3/IC4/IC5/U1 and its rework), the 1861's DMA timing, and electrical loading (fan-out, CMOS levels from LS outputs, rise times on long lines).
- **IO card's 1861 has never been tested** on real hardware (`hardware/FABRICATED.md`).

Programs written for a serial terminal send escape codes: `ESC[2J` clears the screen, `ESC[H` homes the cursor, `ESC[row;colH` places it. HBIOS's `outchar` (`firmware/hbios/v1.0.5/sec1.asm`) acts on CR, LF and backspace only and types everything else, so Mike Riley's v5 `cls` showed `[H[2J`, and we wrote our own (`software/elfos-v5/cls/`). The job is a new HBIOS version (1.0.6, a new EPROM): `outchar` notes an ESC, takes in the `[`, the numbers and the final letter without typing them, and acts on the letter. Known so far: (a) clearing the screen and swallowing the codes it does not act on fits the free ROM (207 bytes at FC31-FCFF in 1.0.5); that is all `cls` and `ur` need, with home swallowed while HBIOS types on the bottom line; (b) placing the cursor is the larger part: HBIOS types on the bottom line only (CR goes to 73C0, LF scrolls everything up), so `ESC[H` and `ESC[row;colH` need a screen routine that types at any row and column, and programs that draw a whole screen (`visual02`) expect 80 x 24, not 64 x 16; (c) the state between characters needs a place in RAM that LF does not wipe: LF clears 73C0-77FF and then rewrites the cursor pointer at 77FE/77FF; (d) of Mike's v5 programs only `cls`, `visual02` and `ur` send any codes (`software/elfos-v5/README.md`); (e) the 64-column wrap fault (below) is in the same screen routine: fix both in one ROM, and decide before burning 1.0.5, so that one burn carries all of it; (f) the VIDEO-G HBIOS (`firmware/hbios/video-g`) wants the same. - **HBIOS 64-column line wrap:** the first character after a wrap is lost, so ELF/OS `DIR` drops every 5th name. Found with the emulator; not fixed.
- **`EDIT` with no file name hangs ELF/OS** (found 2026-10-07, same in the fast and `--hw` emulators). EDIT passes an empty name to the kernel's open (`CALL 0306`); the kernel returns the error, but its return chain pops 6413 instead of EDIT's 20E6, and the 1802 stops on `IDL` in empty RAM. Most likely kernel 0.2.6 build 135's empty-path handling. Workaround: always give a name (`EDIT TEST.TXT`). To do: trace the kernel's open error path, or check a later release in `../private-resources/elf/reference/mike-riley/elfos-releases/`.
- **BIOS probes on ports 2/3:** Mike Riley's BIOS probes for a UART and an RTC on ports 2/3, which on System-5 are the IDE registers. Check that those probes do no harm to the drive.
- **Build the CF card on the Mac instead of from the install EPROM** (Ken, 2026-10-30). **Works on the real machine (2026-11-04):** `software/s5emu/tools/mkelfos.py ~/s5-cf.img --mb 15` for a 16 MB card (exactly 31,360 sectors) in a USB reader, written raw (`diskutil unmountDisk /dev/diskN`, `sudo dd if=$HOME/s5-cf.img of=/dev/rdiskN bs=1m`) and read back clean (`sudo dd if=/dev/rdiskN bs=1m count=15 | cmp - ~/s5-cf.img`). On System-5 at 500 kHz `@FF00` boots to `Elf/OS Ready`, and FREE (3840 total AUs), DIR and `MKDIR X` all work (Ken): the first test of the 1802's own writes to the card. `--mb` counts MiB (2,048 sectors each), so use the largest that fits: `--mb 16` is 32,768 sectors, too big for this card, so `--mb 15` (30,720 sectors, 640 left unused); `--mb 61` for a 64 MB card, whose 125,440 sectors are 61.25 MiB (tested in the emulator 2026-11-04). The image holds FSGEN, kernel 0.2.6 build 135 and Mike's programs in `/` and `/BIN`; edit it later with `disktool`. Before this the card read all zeros, 31,360 of 31,360 sectors with no size stored in sector 0 (backup `~/cf-card-backup-2026-11-04.img`), left by the install ROM's format (below). If it is the `16MB CLS` card of 2026-10-30 (the reader hides the model and serial; `software/busdrv/bringup.py cf` shows them), the 2005 install is gone, and the repo has only the first 64 bytes of its sector 0, in that bring-up report. To do: a manual section (`docs/manual/programmers-guide.md`, "The CF card"), and an `mkelfos.py --card` helper that checks the image and prints the `dd` line. Other cards must accept 8-bit mode (Set Features 01h; many modern CF cards don't: use small older ones). The install EPROM uses 8000-E32E (ELF/OS build in `../private-resources/elf/firmware/elfos-install-rom`); without it the memory card's HI 32K can be RAM.
- **The install ROM's Full format cannot leave a usable disk** (found 2026-11-04 reading the ROM; Ken's own run was on the IC5 ROM, next item). In `../private-resources/elf/firmware/elfos-install-rom/elfos.32k.rom.01`, which asks `<Q>uick or <F>ull ?`, option 1 F writes zeros until a write fails, then stores that count in sector 0; but the failed write leaves ERR set, HBIOS's ready check (FB9A) then refuses both the reset (FB00) and the last write, nothing checks that, and it still prints Complete. In the emulator (ERR held until the next command, as in ATA) the stored size is 0 and option 2 builds a 0-sector filesystem. Quick (IDENTIFY) stores the right size, even straight after a Full. If the card never reports the error, Full never ends; `FBED` waits for DRQ with no timeout, so a card that gives neither hangs there. Use Quick or the Mac.
- **The IC5 install ROM misses the end of the card** (found 2026-11-04). The ROM the repo records in MEM3-E's IC5 (`../private-resources/elf/hardware/memory/eagle/rev-b/bringup/2026-10-30-eprom-ic5-t48-read.bin`, the base of `../private-resources/elf/firmware/elfos-install-rom/with-basic/`) has no Quick/Full prompt: option 1 always makes the full pass. After each write it tests bit 0 of what HBIOS returns, the ATA error register (`SHR` at 9248), not DF. The usual end-of-card errors, IDNF 10h and ABRT 04h, leave bit 0 clear, so it carries on: HBIOS refuses every later write at FB9A, nothing more reaches the card, and the count climbs past the end and wraps at 65,535. It would stop with `E` after 2^29 turns, roughly a month at 500 kHz. Run in the emulator on a 300-sector card with past-the-end writes failing (a scratch test; `machine.py` unchanged): 10h and 04h never finish, 01h finishes. A pass takes about 40 minutes on the 16 MB card at 500 kHz (4,700 machine cycles a sector) plus the card's write time, so days of running was not writing. Every ending leaves all zeros and no size in sector 0, which is what Ken's card read: this is the ROM he ran on the 16 MB card for days (option 1 did not ask Quick or Full; Ken, 2026-11-04). Even when option 1 finishes (01h), option 2 then reports `Total Sectors: 0`, so this ROM cannot make a new card; on a Mac-built card option 2 is fine (30,720 sectors, 3840 AUs). Use the Mac (`docs/manual/operators-guide.md` section 3).
- **Move the 6845 video to E000-EFFF** (Ken, 2026-10-30), with the CF card built on the Mac: RAM 0000-DFFF in one piece (`RRRRRRRRRRRRRR--`, 56K) instead of 0000-6FFF + 8000-EFFF. Needs: MEM3-E's upper RAM fitted (IC11 and its mux IC4, empty today: "MEM3-E" above) and its jumpers moved; 6845 SV1 7-8 instead of 1-2 (RN1 pulls each compare bit high, a jumper grounds it: 7-8 = A12 low = block E); HBIOS rebuilt with `vmem equ 0E000h`, `crtca equ 0E800h` and the hard-coded first cursor `ldi 073h` in `sec1.asm` (store cursor position) changed to `0E3h`, then the CPU EPROM reburned; check the cursor shows (`update` masks the cursor high byte with 3Fh: 73 -> 33 today, E3 -> 23); move every 7000/7800 in the manual, s5emu (`--map`, the 6845 model) and `bringup.py` (`video_base`). Installing from the OS EPROM after the move (RAM 0000-7FFF, EPROM 8000-DFFF): Ken's chip (`../private-resources/elf/hardware/memory/eagle/rev-b/bringup/2026-10-30-eprom-ic5-t48-read.bin`) runs to E084, and E000-E084 would sit under the video. That piece is one program, STAT (133 bytes, loads at 2000): the table at 8000 lists each program as name, 0, ROM start, ROM end, load address, size, exec address, so STAT's entry at 8150 points to E000-E085. Fix: copy E000-E084 into the free gap B57E-BFFF (e.g. B600) and change 8151/8153 from E0 to B6 (two bytes), try the patched ROM's install in the emulator (later, Ken 2026-10-30), then burn a new 27C256. A rebuild from source is not possible today: the repo has the kernel's source (`../private-resources/elf/reference/mike-riley/elfos-kernel-135`) and rcasm, but the utilities only as binaries (`elfos-programs/bin`) and no source for the installer's own code (9000-B57D, the part the table doesn't list). Shifting the whole image down to 7000 instead would mean patching every entry's addresses and any absolute addresses in the installer's own code (no source in the repo). Or install before the move (video at 7000, old HBIOS), or skip the EPROM (CF built on the Mac). Once a card holds ELF/OS the OS EPROM is not needed: HBIOS `@FF00` boots from the card; keep the chip for rebuilding a card without a Mac. Note: `f_freemem` scans up from 0000 to the first byte that won't write, so it ends at the top of the video RAM (77FF today, E7FF then), where HBIOS keeps the cursor; ELF/OS kernel 135 doesn't use it, but programs that do would write over it either way.
